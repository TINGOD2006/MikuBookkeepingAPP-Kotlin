### 需求 2：明細頁帳目單下方紅色方框 → 閒置時必須完全看不到紅色 — **PASS**

**(a) Compose 繪製推理（已回到函式庫原始碼，不採信註解）**

1. `SwipeToDismissBox` 實作（material3 1.3.2 `commonMain/androidx/compose/material3/SwipeToDismissBox.kt:228-254`）：
   - `Box(modifier.anchoredDraggable(...), propagateMinConstraints = true)`
   - `Row(content = backgroundContent, modifier = Modifier.matchParentSize())` ← 背景**被量測成與最外層 Box 同尺寸**
   - 前景 `Row(content = content, modifier = Modifier.draggableAnchors(...))` ← 唯一決定外層 Box 尺寸的子節點
   - 結論：背景高度 ≡ 前景（卡片列）高度，且背景先畫、卡片後畫（同層 children 依序繪製）。
2. 專案端兩處的內縮量必須相同，否則會露出紅邊：
   - 紅底：`BookkeepingScreen.kt:477-492` → `fillMaxSize().padding(vertical = RecordRowVerticalGap).background(MikuColors.Expense, RoundedCornerShape(10.dp))`
   - 白卡：`BookkeepingScreen.kt:507-514` → `fillMaxWidth().padding(vertical = RecordRowVerticalGap).clickableNoRipple(...).background(MikuColors.Card, RoundedCornerShape(10.dp)).padding(10.dp)`
   - `RecordRowVerticalGap = 3.dp`（`BookkeepingScreen.kt:454`，單一定義、兩處共用 `:481`、`:510`）
   - 兩者：寬度同為滿版、垂直內縮同為 3dp、圓角同為 10dp、紅底內縮後矩形 == 白卡背景矩形 → **閒置（offset = 0）時白卡完全覆蓋紅底**。
3. 白卡為**完全不透明**：`ui/theme/Theme.kt:19` `Card = Color(0xFFFFFFFF)`（alpha = FF），不存在紅色由白卡透出的可能。
4. 滑動時紅色仍可見：`draggableAnchors` 讓前景卡片隨手勢水平位移（anchors：`Settled at 0f`、`EndToStart at -width`），卡片左移後右側露出紅底與刪除圖示（`:486-490`）；`enableDismissFromStartToEnd = false`（`:473`）→ 只會往左滑，紅色只從右側露出，與設計一致。

**(b) 滑動回彈不會卡住（同時驗證 `confirmValueChange` 只回 true 於 EndToStart 是否安全）**

- 專案端 `SwipeToTrashRecord`：`confirmValueChange = { if (value == EndToStart) onDelete() else false }`（`BookkeepingScreen.kt:464-469`）
- material3 1.3.2 `commonMain/androidx/compose/material3/internal/AnchoredDraggable.kt:421-435`：`settle()` 在 `confirmValueChange` 回 false 時會 `animateTo(previousValue, velocity)` **回彈**；`:526-533` / `:576-583` 的 `finally` 只在位移已貼齊 anchor（≤0.5px）時才呼叫 confirmValueChange。
- 結論：部分滑動後放開（target = Settled）→ 回彈復位，不會卡在露紅的半途，也不會誤觸刪除。

**(c) 未能在原始碼確認**：白卡與紅底圓角皆走 AA（`drawRoundRect`），兩者同邊界下，圓角弧線上的 1 個抗鋸齒像素理論上可能混到極淡紅色（見第 3 節）。此為像素層級問題，原始碼無法判定，建議實機截圖複驗。

## 2. 確認的缺陷清單（含最小修法建議；本驗收不代改 source）

### D1 —【High】兩個全螢幕編輯畫面不阻擋觸控穿透，編輯中可能被切換成「另一筆記錄」並在儲存時覆寫該筆（資料損毀）

- 位置（無阻擋的畫面）：
  - 明細頁編輯：`BookkeepingScreen.kt:222-228` → `RecordEditorScreen.kt:115-261`（根節點 `Column(Modifier.fillMaxSize().background(...))`，**沒有** `pointerInput` / `clickable` / Dialog）
  - 首頁新增：`MikuApp.kt:138-143`（同樣是普通 `Column`）
  - 全 repo 搜尋 `pointerInput|Popup(` 於 `app/src/main/java` **0 命中**，只有 `AlertDialog`/`DatePickerDialog`（真 Dialog，天然阻擋下層）
- 為什麼錯（繪製／事件模型）：
  1. 編輯畫面是 `BookkeepingScreen` 內 `Box` 之後吐出的**兄弟節點**（`:222-228` 在 `:135-204` 的 Box 之後），因此畫在清單之上，但 **Compose 的 hit test 對沒有 pointerInput 的上層節點不會停止**：compose-ui 1.9.1 `commonMain/androidx/compose/ui/node/InnerNodeCoordinator.kt:208-236` 反序走 `zSortedChildren.reversedAny { ... }`，`if (!wasHit) continueHitTest = true`，要 `hasHit()` 為真才停。
     不命中（＝會穿透）的區域（皆無 pointerInput 且無 clickable 子節點）：
     - 標題列 56dp 內、X 按鈕以外的空白（`RecordEditorScreen.kt:121-151`）
     - 收支切換列的左右 20dp 內距、上下 2dp 縫與該列 36dp 高度中的空白（`:154-186`）
     - 切換列與分類九宮格之間的 `Spacer(8.dp)`（`:188`）
     - 輸入區底色／內距與各 `Spacer`：`:428-433, 455, 500, 504`，以及數字鍵盤每列 `padding(horizontal = 3.dp)` 的 3dp 豎縫、列間 `Spacer(4.dp)`、上下 `Spacer(6.dp)`（`:548-570, 572-599`）
     - 「刪除」與「儲存變更」之間的 `Spacer(8.dp)`（`:526`）
     （相對地，分類九宮格 `LazyVerticalGrid`（`:191-210`）本身帶 scrollable 修飾 → 整個格狀視窗都會命中，該區不會穿透；文字欄位、日期鈕、數字鍵等有 clickable／textField 的地方也不會。）
     → 上述空白處的觸控會繼續往下層兄弟（清單）搜尋，命中所屬的 `LazyColumn` 與該 y 位置的 `RecordRow`（`BookkeepingScreen.kt:507-514` 的 `clickableNoRipple(onClick)`）。
  2. 一旦命中列，`onEdit = { editingRecord = record }`（`:188`）把 `editing` 換成**另一筆記錄**；但 `RecordEditorScreen` 的欄位狀態用 `remember { }` **沒有 key**（`:87-105`），Composition 位置未變 → 不會重新初始化，畫面仍顯示原記錄 A 的分類／金額／備註／日期。
  3. 使用者其後按「儲存變更」→ `update(editing.edited(amount = 畫面顯示的 A 值…))`（`:247-254`）以 **B 的 id** 寫入 **A 的內容** → B 被覆寫、A 的編輯完全遺失，且畫面與 Toast 都顯示成功。
- 影響：靜默資料損毀（非崩潰、非可見錯誤）。觸發機率：編輯時誤觸鍵盤 3–4dp 豎縫或 4–6dp 橫縫即可能發生（輸入區／數字鍵盤位於畫面下半，該區域正後方就是清單列的可點區）。
- 最小修法（兩者並行，成本都低）：
  1. 擋住穿透：將編輯畫面改為 `Dialog(onDismissRequest=…, properties = DialogProperties(usePlatformDefaultWidth = false))` 包住現有內容（獨立視窗天然阻擋下層），或在編輯器根 `Column` 加上會吃事件／至少會被命中的 modifier，例如 `Modifier.pointerInput(Unit) { awaitPointerEventScope { while (true) { awaitPointerEvent() } } }`。**同一個修法要套用到 `MikuApp.kt:138-143` 的新增畫面**（該處穿透會打到下層底部導覽列／FAB，造成背後頁籤被切換）。
  2. 保險：欄位狀態加 key，`remember(editing?.id) { ... }`（`:87-105`），即使未來又發生 `editing` 被換掉，也不會拿 A 的內容去覆寫 B。

### D2 —【Medium】日期選擇器初始值用「本地時區午夜」，Material3 以 UTC 解讀 → 東半球時區顯示／回存日期少一天，且可能跨月

- 位置：`RecordEditorScreen.kt:264-267`
  ```kotlin

      initialSelectedDateMillis = date.atStartOfDay(ZoneId.systemDefault()).toInstant().toEpochMilli(),

  ```
  以及確認回寫 `:273-275`（`Instant.ofEpochMilli(it).atZone(ZoneId.of("UTC")).toLocalDate()`，**這行是對的**）
- 為什麼錯：Compose `DatePicker` 的 `initialSelectedDateMillis`／`selectedDateMillis` 語意是「**UTC** 當日 00:00 的 epoch millis」。material3 1.3.2 `androidMain/androidx/compose/material3/internal/CalendarModelImpl.android.kt`：`getCanonicalDate(timeInMillis) = Instant.ofEpochMilli(timeInMillis).atZone(utcTimeZoneId).toLocalDate()`。

### D3 —【Low】`update()` 失敗被靜默吞掉，且 `update` 未保護 `deletedAtMillis`（未來呼叫端可讓垃圾桶記錄復活）

### D4 —【Low】Flutter 移轉時，舊 JSON 沒有 `id` 的記錄以 `legacy_$dateMillis` 當 id，同日多筆會被 `add()` 靜默丟棄

## 3. 無法從原始碼確認的項目（**本輪沒有實機／模擬器**）

1. **返回手勢的實機行為**：修正後路徑已統一，但「使用者原本遇到的是 IME 先吃掉手勢、還是未 opt-in 的 callback 被平台丟棄」只能靠實機分辨。建議驗收步驟：開啟 App → 按中央 FAB → 直接（不碰備註欄）由螢幕左／右邊緣滑入 → 應回到明細頁；再測「先點備註欄叫出系統鍵盤 → 滑一次收起鍵盤 → 再滑一次回明細頁」，以及「編輯既有記錄」與「已自動記錄」確認頁各一次。
2. **數字鍵盤的實機可觸性**：`imePadding` 依賴 API 30+ 的 IME insets 回報；minSdk 26–29 的裝置回報較不可靠（`SearchScreen` 早已依賴同樣行為）。極矮視窗（橫向）仍需手動捲動才能看到鍵盤——可捲動、不阻擋，但「自動捲動」只在選分類的瞬間觸發。
3. **標題列現在會隨內容一起捲動**（為了讓「橫向／極矮視窗＋IME」時可視高度不為 0 的刻意取捨），實機外觀需確認是否可接受。
4. `withFrameNanos` 的自動捲動時機屬 best-effort：失敗只會「不自動捲」，仍可手動捲到鍵盤。
5. 分類預算只能對「目前存在的支出分類」設定：已刪除的分類、或收入分類不會出現在清單（僅顯示不到，不影響其他功能）。
